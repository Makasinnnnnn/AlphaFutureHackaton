# Стратегия команды: умный кредитный кабинет

Обновлено 21 октября 2026. Основание: PDF кейса, приложенный репозиторий, запуск доменных тестов и пограничных примеров, публичные источники о прошлых соревнованиях. Команда: 5 человек с базовыми навыками и ИИ-инструментами; ориентир доступности — 50–100 человеко-часов. Работа через общую доску со свободным выбором задач, без жёсткого распределения специализаций.

## 1. Решение за две минуты

1. **Код друга — не хуйня.** Это содержательная основа: клиент, аналитик, отдельные скоринг и решение, конвейер, PostgreSQL, симуляторы и документация. Переписывать всё сейчас невыгодно.
2. **Готовность к сдаче не доказана.** В этом разборе прошли 26 доменных тестов, но полный Docker/E2E и браузерный путь не проверены. Найдены реальные пробелы в проверке выписок и ручном дозапросе.
3. **Рекомендуемый продукт:** «Кредитный маршрут — от потребности бизнеса к выполнимым условиям финансирования». Пользователь понимает, что доступно, почему предложены такие условия и какое действие требуется дальше.
4. **Главный демонстрационный момент:** сохранить нужную сумму, предложив подходящий срок; показать изменение платежа, переплаты и условий, а затем пройти до выдачи в симуляции.
5. **Приоритет:** целый путь → корректность данных и решений → понятные объяснения → доказательства пользовательской пользы → дополнительные AI-возможности.
6. **Оставить текущий стек.** React/TypeScript + FastAPI + PostgreSQL + отдельный worker + локальные mocks + Docker Compose подходят этому MVP.
7. **Не добавлять обязательную LLM-зависимость.** По кейсу ML не обязателен; если LLM используется, нужны открытые веса и автономная проверяемая версия.
8. **Обсудить сегодня:** основного пользователя, главный выигрыш для него, один основной сюжет демонстрации и границу функций до дедлайна. Ниже есть вопросы и готовый порядок обсуждения.
9. **Командная работа:** GitHub Issues + Projects; каждый сам берёт карточку. Один владелец взятой задачи, небольшие PR и подтверждение результата перед Done.
10. **Победу нельзя обещать.** Эта стратегия повышает качество и проверяемость заявки; состав соперников, оценки жюри и дополнительные инструкции платформы неизвестны.

## 2. Что от вас обязательно ждут

Основной источник — страницы 6–7, 9–11 и 13–15 кейса: PDF кейса, предоставленный команде

| Требование | Что должно происходить в работающей системе | Как доказать |
|---|---|---|
| Исследование потребностей | Понятно, кому и какую проблему решаете | Реальные наблюдения/интервью и связь «потребность → функция» |
| Кабинет клиента | Выбор продукта, заявка, результат и дальнейшие действия | Эксперт сам проходит сценарий |
| Банковская обработка | Проверка полноты, этапы рассмотрения, данные и решение | Изменение статусов, проверки, рабочее место банковской стороны |
| Согласованность | Данные сохраняются и используются дальше | Обновление страницы, повторный вход, продолжение заявки |
| Модель процесса | Определены границы, роли, переходы, исходы | Диаграмма состояний совпадает с кодом |
| Модель решения | Риск оценивается отдельно от условий продукта | Один профиль может получать разные условия по продуктам |
| Enterprise-подход | Безопасность, надёжность, устойчивость и сопровождение | Проверки доступа, повторов, ошибок источников, аудит, воспроизводимый запуск |
| Готовность к проверке | Прототип можно запустить на обычном ПК | Docker, инструкции, синтетические данные, понятный сценарий |

В PDF нет числовых весов критериев, обязательной конкретной ML-модели, заданного языка программирования, требования Kafka/Kubernetes и точного обязательного количества кредитных продуктов. Пожелания автора README не превращаются в требования организаторов.

Сквозной путь нужно показывать связно: потребность → продукт → черновик → отправка → полнота/дозапрос → обогащение → скоринг → решение → принятие предложения → договор → подпись и выдача в допустимой симуляции. Число промежуточных стадий зависит от вашего MVP. Ручной аналитик — сильное решение для исключений и банковского опыта, хотя конкретный интерфейс аналитика как отдельный обязательный экран в PDF не предписан.

### Ограничения, которые нельзя потерять

- Клиентская часть — веб; реализация продукта мобильным приложением не допускается. Адаптация веб-экрана под узкий браузер сама по себе не является мобильным приложением.
- Корпоративные системы банка не требуются: внешние проверки воспроизводятся локальными mocks/stubs/симуляторами.
- Данные, документы, сотрудники и компании — синтетические.
- Проверяемая версия не зависит от платных API, подписок, покупных данных и закрытых корпоративных лицензий.
- LLM допускаются только с открытыми весами. Код приложения, который вызывает Claude/OpenAI/DeepSeek API во время проверки, нужно оценивать отдельно на соответствие этому ограничению; название провайдера само по себе ничего не доказывает.
- Основной путь целиком внутри продукта: email, SMS, телефон и мессенджеры не являются этапами оформления.
- Подписание и перечисление денег разрешено моделировать; это нужно явно обозначить.
- Платные инструменты, используемые только при разработке, исключены PDF из ограничения платных ресурсов проверяемого решения.

**Переносимый вывод:** сначала понять способ проверки и дать проверяемый результат. Полезна способность системы явно сообщать о недостатке данных. Для вашего кейса это значит: честный дозапрос или ручное рассмотрение вместо выдуманного одобрения. Из источников не следует, что победу обеспечили чат-бот, определённый фреймворк или самая большая модель.

### Практическая стратегия на основе истории и вашего PDF

1. Закрыть способ проверки текущего кейса: запустить, пройти, проверить состояние и данные.
2. Показывать решения на сравнительных примерах, включая отказ и недостающие данные.
3. Сохранить журнал экспериментов и изменений: какая проблема обнаружена, что исправлено, чем подтверждено.
4. Подготовить короткую защиту причин выбора MVP и его границ.
5. Не строить продукт по списку технологий прошлых команд. Для вашего кейса главным источником требований остаётся PDF 2026 года.

## 4. Рекомендованный концепт

**Рабочее название:** «Кредитный маршрут». Название можно поменять; обязательства продукта важнее брендинга.

**Пользователь:** собственник или представитель действующего малого/микробизнеса, которому нужно финансирование закупки либо оборудования. В первой версии сосредоточиться на одном основном сегменте, подтверждённом интервью. Не пытаться одновременно одинаково хорошо обслужить стартап без истории, среднюю компанию и крупный холдинг.

**Задача пользователя:** «Мне нужна определённая сумма на понятную задачу. Я хочу увидеть выполнимый вариант, необходимые документы и следующий шаг, не начиная оформление заново после каждого изменения условий».

**Обещание:** объяснить доступный маршрут финансирования и довести заявку до результата. Предварительная оценка должна быть помечена как предварительная, а условия после рассмотрения — отделены от неё. Нельзя обещать реальное банковское одобрение, вероятность выдачи или конкретный срок рассмотрения без основания.

| Направление | Польза | Риск за оставшееся время | Решение |
|---|---|---|---|
| Полный кабинет с множеством разделов | Покрытие большого числа сценариев | Долгая интеграция, слабая глубина | Ограничить основным кредитным путём |
| Общий AI-чат о финансах | Удобный свободный ввод | Ошибочные советы, требования к модели, слабая связь с заявкой | Только необязательное дополнение |
| Понятные условия + исполнение дозапроса + управляемые исключения | Связано с задачей обеих сторон и текущим кодом | Нужно аккуратно согласовать данные и статусы | **Основной вектор** |
| Сложная ML-модель риска | Исследовательская глубина | Нет исторических данных о дефолтах и достоверной валидации | Оставить прозрачную балльную модель |

Это сравнительная оценка для вашей команды, а не измеренная оценка жюри или рынка.

### Три опорные функции

**1. Сравнение выполнимых условий.** На одном экране: исходная сумма/срок, предложенные сумма/срок, платёж, полная сумма платежей, переплата и понятная причина изменения. Для овердрафта нужна отдельная корректная модель отображения: не притворяться обычным аннуитетным кредитом.

**2. Понятная карта данных и дозапроса.** У каждого блока указаны источник, период, актуальность и статус проверки. Если нужен документ, пользователь видит конкретный пункт, причину, допустимый формат и подтверждение исполнения. Если данные не получены, интерфейс не превращает отсутствие сведений в положительный факт.

**3. Объяснимое решение с работой аналитика.** Аналитик получает данные, проверки, вклад факторов, ограничения и историю. Ручное изменение условий требует обоснования и остаётся в аудите. Клиенту показываются существенные причины и действия, без раскрытия всей внутренней риск-модели.

### Конкретный сюжет уже поддерживается моделью

На синтетическом профиле из проверенного примера: поступления 600 000 ₽/мес., существующие платежи 100 000 ₽/мес., сумма 1 500 000 ₽, запрос на 6 месяцев, демо-ставка 19%. Текущая модель даёт 85 баллов и предлагает ту же сумму на 9 месяцев.

| Вариант | Новый платёж | Вместе с существующими платежами |
|---|---:|---:|
| Запрошенные 6 месяцев | 264 035,51 ₽/мес. | 364 035,51 ₽/мес. |
| Предложенные 9 месяцев | 180 137,39 ₽/мес. | 280 137,39 ₽/мес. |

По демо-правилу нагрузка должна укладываться в половину поступлений, то есть 300 000 ₽/мес. Это иллюстрация логики прототипа, не банковский норматив и не предложение Альфа-Банка. Более длинный срок увеличивает срок обязательств и обычно суммарные проценты: это тоже нужно показать, а не только уменьшившийся платёж.

### Что можно добавить после обязательного пути

Предварительный сценарный расчёт суммы/срока без создания множества заявок. Он должен использовать тот же расчётный слой, что итоговое решение, и показывать ограничения актуальности. Не вводить «вероятность одобрения 93%», если у вас нет валидированной вероятностной модели.

Open-weights LLM может преобразовывать свободное описание цели в структурированный запрос или объяснять уже полученный результат. Числа и условия берутся из расчётного слоя; модель не назначает ставку и не переопределяет отказ. Сбой модели не блокирует заявку. При нехватке времени достаточно существующего подбора по правилам.

## 5. Честная оценка прототипа друга

Оцениваю переданный код, а не качество неизвестного мне промпта и не бренд использованной модели.

| Область | Оценка по найденным фактам |
|---|---|
| Архитектурный каркас | Уместен для MVP; выделены домен, сервисы, API, worker, mocks |
| Покрытие кейса | Широкое: обе стороны, несколько исходов, сохранение, аудит и комплект документов |
| Кредитная логика | Разделение риска и продуктовых правил сделано правильно; модель экспертная, не обученная |
| Защита изменений | Есть версии, блокировки, ограничения параметров и идемпотентность; полное конкурентное поведение ещё нужно проверить |
| Пользовательское исследование | Пока гипотезы; раздел результатов интервью — заготовка |
| Корректность данных | Есть воспроизведённые пробелы, перечисленные ниже |
| Эксплуатационная готовность | Не подтверждена полным запуском на чистой машине |
| Отличие продукта | Пока во многом хороший типовой кредитный конвейер; нужно яснее показать пользовательский выигрыш |

**Вердикт:** оставить основу, исправить найденные дефекты и усилить один понятный сценарий. Красивые документы и 26 зелёных доменных тестов не заменяют сквозной проверки, но и не делают весь проект бесполезным.

B04 — воспроизведённый результат доменной функции, а не доказательство выдачи сверх лимита: срок предложения изменился, метаданные не объясняют этот переход.

### Что проверено и что осталось неизвестным

- Прошли **26 случаев `tests/test_domain.py`** в отдельном Python-окружении с pytest 9.1.1.
- Проверены положительное решение, три стоп-фактора, аннуитет, приложенные CSV и новые пограничные примеры.
- Документация заявляет 41 тестовый случай; оставшиеся API-тесты в этом разборе не выполнялись.
- Docker Desktop был запущен для проверки, однако подтверждение готовности движка и работающего полного стека не получено. Docker Compose, миграции на PostgreSQL, API/E2E и UI нельзя считать успешно проверенными.
- Нет доказательств производительности, пригодности скоринга для реального портфеля, защиты от всех злоупотреблений или реальной юридически значимой подписи. Для конкурсного MVP часть этого допустимо моделировать при явных границах.

## 6. Какие задачи делать в каком порядке

### P0: допускает независимую проверку

Чистый запуск; обе роли и все обязательные переходы; корректные финансовые входы; исполнение дозапросов; сохранение и восстановление; доступ только к своим данным; понятные ошибки. Любой новый дизайн должен сохранять этот путь.

### P1: объясняет ценность

Сравнение исходных и выполнимых условий, корректные объяснения и источники данных; короткое исследование пользователей; финальная демонстрация и комплект сдачи; минимальный CI и проверка повторных действий.

### P2: только после предыдущего

Предварительный what-if, OCR ограниченного набора форматов, языковой помощник с оценкой качества, дополнительные продуктовые сценарии. Наличие P2 не должно мешать сдаче без модели и GPU.

**Стоп-лист на отбор:** миграция стека, новый брокер событий без доказанной необходимости, обязательная облачная зависимость, чат-бот общего назначения, обучение скоринга на случайно сгенерированных «дефолтах», добавление новых разделов кабинета ради количества экранов.

## 7. Что обсудить с командой сегодня

Встреча на 40–50 минут; результат фиксировать в журнале решений. Все обсуждают и выбирают задачи свободно.

| Время | Вопрос | Какой ответ должен остаться |
|---|---|---|
| 0–10 мин | Кому помогаем и в какой ситуации? | Один основной сегмент и конкретная потребность |
| 10–20 мин | Что человек сможет сделать лучше благодаря нам? | Один проверяемый результат вместо списка функций |
| 20–30 мин | Что показываем жюри от начала до конца? | Основной сценарий + два исключения |
| 30–40 мин | Что уже есть, что сломано, что не успеваем? | Карточки P0/P1 с критериями приёмки |
| 40–50 мин | Что каждый берёт первым? | До пяти небольших задач в работе, без пересечения файлов без согласования |

Вопросы для выбора направления:

1. Основной пользователь — существующий клиент банка или бизнес с выпиской из другого банка? Какой путь будет главным на демонстрации?
2. Его первая потребность — подобрать продукт, понять посильный платёж или убрать неопределённость после подачи? Какие реальные слова пользователя это подтверждают?
3. Достаточно ли показать закупку товара как главный сюжет, а оборудование — как дозапрос/залог? Овердрафт оставить вторым планом?
4. Что является нашим главным обещанием и чего мы не обещаем до решения банка?
5. Какие сведения уже известны системе и какие действительно должен вводить клиент?
6. Как показываем устаревшие, неполные и противоречивые данные?
7. Когда автоматизация должна остановиться и передать решение человеку?
8. Что именно считается выполнением ручного дозапроса?
9. Что клиент увидит при отказе, чтобы понимать допустимые следующие действия?
10. Как сравним наш путь с обычной формой и докажем улучшение?
11. Какая функция будет первой удалена, если времени окажется меньше?
12. Сможет ли каждый из пяти объяснить скоринг, контрпредложение, mocks и симуляцию выдачи без подсказки ИИ?

## 8. Кого и как опросить

Рекомендация для вашей команды: 3–5 предпринимателей/бухгалтеров с недавним опытом заявки и, если доступен, 1 человек с опытом кредитной аналитики. Это исследовательская цель, не обязательное число из PDF. Не искать реальные банковские документы и чувствительные данные — достаточно описания опыта и теста синтетического прототипа.

Вопросы интервью:

1. Вспомните последнюю потребность в финансировании: что случилось, сколько было времени и как выбрали способ решения?
2. Как определяли сумму и срок? Кто участвовал?
3. Какие данные и документы собирали? Что вводили повторно?
4. На каком этапе возникала неопределённость? Что делали, чтобы узнать состояние?
5. Были ли дозапрос, отказ или предложение других условий? Что вы поняли из объяснения?
6. Что оказалось важнее в той ситуации: сумма, платёж, срок, цена или скорость? Почему?
7. С чем сравнивали кредит? Когда решили отказаться от него?
8. Покажите, как вы выполнили бы заданную задачу в прототипе. Не объяснять интерфейс заранее.
9. Своими словами объясните предложенные условия и следующий шаг.
10. Что в показанном пути осталось непонятным или не вызывает доверия?

Не спрашивать «нравится ли наш AI» и «пользовались бы вы удобным кабинетом»: такие ответы слабо помогают выбрать продукт. Фиксировать роль, контекст, наблюдение, короткую точную цитату при согласии, вывод и изменение продукта. Не придумывать интервью и положительные отзывы.

### Минимальная проверка гипотез

| Гипотеза | Эксперимент | Целевой сигнал; пока не результат |
|---|---|---|
| Изменение срока понятно без менеджера | Дать контрпредложение без подсказок | 4 из 5 участников правильно объясняют платёж, срок и компромисс |
| Дозапрос позволяет продолжить оформление | Попросить исполнить конкретный пункт | Пользователь находит нужное действие, данные сохраняются, маршрут продолжается |
| Источники данных уменьшают неопределённость | Показать заполненный профиль с источниками | Пользователь отличает известные банку сведения от введённых им |
| Аналитику хватает контекста | Дать карточку исключения и попросить принять решение | Он может объяснить проблему и действие по видимым данным |

На маленькой выборке не заявлять статистически доказанный рост конверсии. Если доступны только товарищи без предпринимательского опыта, назвать это проверкой понятности интерфейса, а не подтверждением потребностей бизнеса.

## 9. Общая доска GitHub: как работать без жёстких ролей

Рекомендуем GitHub Projects, связанный с Issues и PR. [GitHub описывает](https://docs.github.com/en/issues/planning-and-tracking-with-projects/learning-about-projects/about-projects) таблицу/доску, поля и связь с задачами. [Репозиторий команды](https://github.com/Makasinnnnnn/AlphaFutureHackaton) и [общая доска](https://github.com/users/Makasinnnnnn/projects/4) подключены. Исходники ещё нужно перенести в репозиторий; задачи и документация относятся к анализу переданного архива.

Колонки: **Ideas → Ready → In progress → Review → Done**, отдельно **Blocked**. Поля: Priority P0/P1/P2, Estimate S/M/L, Assignee, Due, Depend on. Категории меток: bug, feature, research, docs, qa, release. Названия меток — предложение для настройки, а не уже созданные объекты GitHub.

- Каждый может предложить новую карточку в Ideas. До переноса в Ready добавить проблему, результат, приёмку и зависимости.
- Каждый может взять Ready-карточку: назначить себя и перевести в In progress. Постоянных «владельцев фронта/бэка» нет.
- Одна активная задача на человека. Если нужен помощник — указать его в карточке и согласовать границы правок.
- Задачи преимущественно на 1–4 часа; крупные делить по проверяемому результату. Оценки приблизительны, ИИ не отменяет время интеграции.
- PR связан с карточкой. Проверку выполняет другой участник; ревьюер тоже выбирается свободно.
- В Done попадает проверенный результат: ссылка на PR/коммит и тест/скринкаст/наблюдение. «ИИ написал» не является критерием готовности.
- Два коротких сверочных сеанса в день: блокеры, конфликтующие изменения, состояние общего сценария. Приоритетные задачи берутся раньше косметики.

## 11. Инструменты: что использовать

| Задача | Подход |
|---|---|
| Генерация и проверка кода | Codex/Claude/другие ассистенты в разработке; фиксировать результат в Git и проверять самостоятельно |
| UI | Текущий React/TypeScript; Figma при необходимости согласовать сложный экран |
| API/домен | Текущий FastAPI, Pydantic, чистые функции расчёта, pytest |
| Данные и процесс | PostgreSQL, Alembic, текущий worker, явные переходы и аудит |
| Проверка продукта | Docker Compose, браузер, Playwright, реальные проходы обеих ролей |
| Интеграции | Локальные симуляторы с задержкой, ошибкой, отсутствием данных |
| Распознавание | Сначала строгий CSV; PDF/OCR только с ограниченным набором форматов и резервом времени |
| ИИ в продукте | Только соответствующая условиям open-weights модель; основной сценарий должен работать без неё |
| Командный контекст | GitHub Issues/Projects, короткий AGENTS.md, CONTEXT, журнал решений |

По ресурсному ограничению PDF платный ассистент разработки не становится запрещённым платным API проверяемого приложения. Это не заменяет проверку общего регламента 2026 на требования к авторству и заимствованиям.

MCP использовать по задаче: GitHub — карточки/PR; Serena — навигация по коду; Context7 — документация; Playwright — сценарии; Chrome DevTools — console/network/performance; Mermaid — схемы; context-mode/MarkItDown — материалы. Остальные подключённые серверы не нужно вызывать ради количества. Локальные настройки MCP и ваши учётные данные не входят в проверяемый банковский продукт.

## 12. Общий контекст для пяти ИИ

**Рекомендация:** один GitHub-репозиторий с общей документацией, каждый работает из своего клона/ветки и своего ИИ-аккаунта. История одного чата и локальная MCP-память не являются автоматически общей памятью команды.

Подготовлен переносимый пакет [team-context](README.md): короткая инструкция для агентов, факты кейса, предлагаемые решения и backlog. Его можно перенести в корень репозитория, аккуратно объединив инструкции с существующим AGENTS.md.

[Документация Codex](https://developers.openai.com/codex/guides/agents-md) подтверждает загрузку AGENTS.md по области проекта. Большой аналитический документ не стоит целиком превращать в автоматическую инструкцию: короткий файл должен указывать, что читать по задаче. У других ассистентов нужно проверить их механизм загрузки инструкций либо явно попросить прочитать эти файлы.

Предлагаемая структура: `AGENTS.md` → `docs/team/CONTEXT.md`, `docs/team/DECISIONS.md`, ссылка на живую доску → подробная стратегия по необходимости. После появления доски статус задач хранится в GitHub; локальный BACKLOG остаётся исходным планом, чтобы не вести два противоречащих трекера.

Каждый запрос ИИ должен содержать: ссылку/номер задачи, цель, критерии приёмки, границы файлов/API и способ проверки. После работы — что изменено, чем проверено, ограничения и обновлённый контекст. ИИ не должен самостоятельно превращать предложенный концепт в уже утверждённое решение команды.

Общий проект/папка в приложении может облегчить организацию, но факт общего названия не даёт другим участникам доступ к локальному коду и всем чатам. Рабочей основой передачи контекста сделать Git и проверенные файлы. Аккаунты, токены и абсолютные личные пути из `~/.codex/config.toml` в репозиторий не копировать.

## 13. План до 26 октября и ограничение объёма

Это последовательность контрольных результатов, а не назначение постоянных ролей. Любой участник может взять подходящую карточку.

| Дата | Контрольный результат |
|---|---|
| 21 октября | Выбран основной сюжет; заведены P0; получен воспроизводимый запуск либо конкретный список блокеров |
| 22 октября | Выписки и ручной дозапрос исправлены; основной путь проходит без подсказок разработчика |
| 23 октября | Сравнение условий и понятные причины готовы; первые интервью/наблюдения разобраны |
| 24 октября | Сквозные исключения, доступы, повторы и восстановление проверены; UI уточнён по наблюдениям |
| 25 октября | Заморозка функций; чистый клон, комплект сдачи, версия, демо и запасной сценарий |
| 26 октября | Повтор ключевого smoke-теста и сдача заранее относительно подтверждённого времени закрытия |

Планирование при нижней границе времени: примерно 35–40 часов на обязательные исправления, проверку, объяснение условий и комплект; 10–15 часов оставить на интеграционные проблемы и повторную проверку. Это начальная оценка, не гарантия; после первого чистого запуска переоценить карточки.

При доступных 80–100 часах остаток направить на what-if и дополнительное исследование, если P0 закрыты. Если чистый запуск не получен за первый рабочий блок, остановить расширение функций. Если нет сквозного пути к концу 23-го — убрать OCR/новый AI и необязательный продуктовый охват. Сокращать дополнительный функционал, сохраняя связность процесса.

## 14. Как демонстрировать

Рекомендуемый сценарий на 5–7 минут, если платформа не задаёт другой формат:

1. **Проблема, 30 секунд:** пользователь хочет нужную сумму и понятные условия; банк должен безопасно провести рассмотрение. Показать конкретное наблюдение исследования, если оно получено.
2. **Основной путь, 2 минуты:** потребность → данные/источники → заявка → решение → сравнение условий → принятие → договор → симуляция выдачи. Обновить страницу, показав сохранение.
3. **Исключение, 1 минута:** конкретный дозапрос, загрузка корректного документа, подтверждение исполнения, продолжение.
4. **Банковская сторона, 1 минута:** недоступность БКИ или пограничная заявка → аналитик видит причину, принимает обоснованное решение → клиент получает результат.
5. **Доказательства, 1 минута:** результаты тестов, границы модели, Docker, схема процесса, какие действия автоматизированы и что смоделировано.

Видео — резерв, работающий продукт — основа. Подготовить синтетические данные для каждого сценария и понятный сброс демо. Не очищать общую БД перед демонстрацией случайной командой и не выдавать искусственную паузу worker за реальное время банковского рассмотрения.

### Какие показатели собирать

Время и успешность выполнения конкретных задач в UX-тесте; число ручных вводов; долю тестовых сценариев, прошедших полностью; исполнение дозапроса; отсутствие дублей при повторах; восстановление после сбоя. Время вычисления в демо измерять отдельно от реального кредитного SLA. Проценты на синтетических персонажах не являются прогнозом реальной конверсии или риска банка.

## 15. Что спросит жюри

| Вопрос | Суть честного ответа |
|---|---|
| Почему такая модель? | Нет реальных дефолтных данных; правила прозрачны, отделены от условий продукта и проверяются сценариями |
| Чем отличаетесь от обычной заявки? | Показываем выполнимые условия, источник данных и конкретное действие; доказательство — основной сценарий и наблюдения пользователей |
| Почему не всё решает AI? | Решение воспроизводится расчётным слоем; языковой помощник имеет ограниченную роль |
| Что при отказе источника? | Конечное состояние и маршрут к специалисту, сохранённая причина; показать это работающим |
| Как защищены данные клиента? | Проверка роли и компании, ограничения доступа к документам, проверенные отрицательные сценарии |
| Что при повторной отправке/двух аналитиках? | Идемпотентность/версия/транзакции; отвечать только тем, что реально проверено |
| Умеете читать любые документы? | Нет: перечислить поддержанные форматы и политику отказа |
| Это настоящий кредит и подпись? | Нет, это разрешённая конкурсная симуляция с явно описанными границами |
| Как оценили пользу? | Показать метод, размер выборки, реальные результаты и ограничения исследования |
| Что будет следующим? | Приоритет подтверждённой потребности; реальные интеграции и калибровка модели требуют отдельной работы |
