# Начальные карточки общей доски

Исходный план карточек для [доски](https://github.com/users/Makasinnnnnn/projects/4). Актуальные статусы и исполнители находятся на доске. Участники сами выбирают задачи и могут добавлять новые. Идентификаторы HACK-XXX — локальные ключи для предотвращения дублей, не номера GitHub issues. Машиночитаемый вариант — `backlog.json`.

Оценки приблизительны. S ≈ 1–2 часа, M ≈ 2–4 часа, L требует разбить работу, если не укладывается в один проверяемый результат. Все карточки без назначенных исполнителей. Статус Ready ниже означает готовность начать после получения кода; зависимости всё равно нужно проверить.

## Критерии карточек

### HACK-001 — Воспроизводимый запуск

Проблема: конфигурация есть, успешный полный запуск пока не подтверждён. Приёмка: новый клон/копия без скрытого локального состояния запускается документированной командой; healthchecks проходят; обе роли входят; логи и версии сохранены. Проверить также повторный запуск. Если есть блокер — точная ошибка, воспроизведение и исправление. Не считать «контейнер существует» успешным запуском продукта. Не трогать посторонние контейнеры и тома.

### HACK-002 — Конечные суммы

Проблема воспроизводится на `NaN` и `inf` в CSV. Приёмка: такие значения и их варианты не сохраняются, пользователь получает понятную ошибку с проблемной строкой/полем; обычные CSV продолжают работать. Проверить API, отсутствие частичного обновления и тесты парсера. Не ограничиваться исправлением отображения NaN на фронтенде.

### HACK-003 — Период выписки

Согласовать D006: актуальный период, число необходимых месяцев, допустимость пропусков и нулевых месяцев. Приёмка: будущие операции отклоняются; три месяца с многолетними разрывами не считаются достаточной последовательной историей; даты и предупреждения понятны пользователю. Проверить границы месяцев/года и обычную шестимесячную выписку. Не выдавать выбранную политику за требование PDF или норматив банка.

### HACK-004 — Ручной дозапрос

Проблема: ANALYST_REQUEST можно повторно отправить без исполнения, а стандартная валидация не сохраняет его смысл. Приёмка: у запроса есть проверяемый способ ответа/документ и состояние; пустая отправка запрещена на API и UI; ответ сохраняется; маршрут возвращает заявку нужному участнику; история запроса и ответа видна. Проверить, что исправление не ломает обычный запрос выписки и документов оборудования.

### HACK-005 — Постоянная ошибка worker

Приёмка: искусственная постоянная ошибка не оставляет заявку в бесконечных повторах; после заданного предела есть конечный маршрут, причина и действие оператора; другие заявки обрабатываются. Повтор временной ошибки работает. Добавить понятную конфигурацию/документацию и проверку без ожидания реальных минут.

### HACK-006 — Лимиты контрпредложения

Пример: 1,5 млн на 6 месяцев меняется на 9, а метаданные dti-лимита остаются для 6 месяцев. Приёмка: API и аналитик различают запрос и предложение либо показывают пересчитанные лимиты; причины и сумма согласованы; регрессионная проверка покрывает изменение срока и суммы. Не менять кредитные правила ради сокрытия несогласованных метаданных.

### HACK-007 — Сквозные сценарии

Приёмка: заявка до симуляции выдачи; дозапрос и продолжение; контрпредложение; ручное решение; отказ по стоп-фактору. Пройти API и браузерные действия обеих ролей, включая обновление страницы и повторный вход. Сохранить результат/скринкаст и команды запуска. Тестовая БД изолирована от демо-данных.

### HACK-008 — Сравнение условий

Приёмка: в решении видны исходные и предложенные сумма, срок, платёж, общая стоимость/переплата и причина изменения; явное действие принять либо отказаться; математические значения приходят из общего расчёта. Овердрафт имеет корректное отдельное представление. Проверить основной пример и нулевые/отсутствующие данные.

### HACK-009 — Данные и следующие действия

Приёмка: клиент видит происхождение и период существенных сведений, недоступность источника отличима от отсутствия отрицательных признаков; для каждого существенного состояния понятны смысл и доступное действие. Полные веса/внутренние правила не раскрываются случайно. Текст соответствует реальным переходам.

### HACK-010 — Сегмент и интервью

Приёмка: выбран и обоснован основной сегмент; сохранены реальные краткие заметки 3–5 интервью, если удастся привлечь подходящих людей, либо честно указан меньший фактический объём; выделены повторяющиеся проблемы и контрпримеры. Число интервью — цель команды, не формальность кейса. Итогом может быть изменение концепта. Реальные чувствительные документы не нужны.

### HACK-011 — Проверка понятности

Приёмка: участникам без подсказки дают понять контрпредложение и исполнить дозапрос; записаны фактические результаты и затруднения, размер/состав выборки, внесённые изменения. Не превращать маленькую выборку в доказательство реальной банковской конверсии. Участников без бизнес-опыта описывать как UX-тест, не CustDev бизнеса.

### HACK-012 — CI

Приёмка: зафиксированная установка, доменные/API-проверки с отдельной PostgreSQL при необходимости, frontend typecheck/build; логи доступны в PR. Выбрать минимальный устойчивый набор. Не запускать тестовую fixture на общей или демонстрационной БД: она удаляет указанную тестовую базу.

### HACK-013 — Доступы и повторные действия

Приёмка: клиент не читает/меняет чужую заявку и документ; клиент не вызывает аналитические действия; повторное создание/отправка не дублируют результат; устаревшая версия решения не перезаписывает новую; недопустимые переходы отклоняются. Фактические тесты и статусы HTTP сохранены.

### HACK-014 — Отказы и восстановление

Приёмка: задержка/ошибка БКИ приводит к объяснимому маршруту; рестарт worker продолжает заявку без повторной выдачи; необязательный языковой помощник выключен/сломался, а основной путь работает. Не заявлять отказоустойчивость только по наличию restart-политики.

### HACK-015 — Комплект сдачи

Приёмка: README, схема, API/OpenAPI/коллекция, состояния, модель данных, сценарии, учётки, синтетические данные, THIRD_PARTY_NOTICES и lock-файлы соответствуют проверенной версии. Подтверждены актуальные поля платформы и время сдачи. Нет вымышленных результатов исследований/проверок.

### HACK-016 — Демонстрация

Приёмка: основной сюжет и два исключения укладываются в согласованное время; есть синтетические данные, сценарий сброса, запасная запись; каждый желающий может объяснить ключевые допущения. Фактические функции отделены от планов. Не выдавать искусственную паузу конвейера за реальный банковский SLA.

### HACK-017 — Версия и доступ

Приёмка: реальный GitHub открывается участникам и жюри согласно правилам; выбранный commit hash сохранён, заявленный тег существует; финальная версия воспроизводится. Приватный доступ жюри проверяется отдельно, без изменения публичности репозитория по умолчанию. После дедлайна сдаваемая версия не подменяется.

### HACK-018 — What-if

Только после основных сценариев. Приёмка: сумма/срок пересчитываются тем же слоем, что решение; расчёт явно предварительный, содержит существенные ограничения и не создаёт новую заявку на каждый ввод. Нет выдуманной вероятности одобрения. Показать разницу платежа и общей стоимости.

### HACK-019 — Языковой помощник

Только если подтвердится потребность. Приёмка: модель с открытыми весами и проверенной лицензией, согласованная аппаратная среда, измеренные задержка/качество, fallback. На тестовом наборе помощник не выдумывает условия и не меняет решение. Платный внешний API не становится необходимой частью сдаваемого продукта.

### HACK-020 — PDF/OCR

Сначала оценить пользу относительно времени. Приёмка: ограниченный явно названный формат распознаётся на синтетических примерах; суммы и даты валидируются; неизвестный формат/низкая уверенность приводит к понятному отказу или ручному подтверждению. Наличие кнопки загрузки PDF не считать распознаванием.
