# Продуктовое обоснование

> Потребности и ожидаемые эффекты ниже — продуктовые гипотезы. Фактические интервью и измеренные эффекты не представлены. Краткий обзор работающего решения: [PRODUCT_OVERVIEW.md](PRODUCT_OVERVIEW.md).

## Условия и ставки демопродуктов

Ставки 17–21% — параметры учебной модели, а не действующие тарифы Альфа-Банка и не оценка рыночной стоимости кредита на дату сдачи. Базовые ставки продуктов заданы в синтетическом справочнике; итоговая ставка = базовая ставка продукта + надбавка категории риска `GRADE_PREMIUM` из `backend/app/domain/decision.py`. Более высокий риск повышает надбавку, а обеспечение и тип продукта отражаются в базовой ставке.

Для реального продукта базу следует калибровать как стоимость фондирования + операционные затраты + целевая маржа, надбавку — по ожидаемым потерям и капиталу. Ключевая ставка может быть ориентиром стоимости фондирования, но прототип её не загружает и не подменяет ею фактические банковские расчёты. Текущие числа выбраны для воспроизводимых демосценариев; их рыночная калибровка не подтверждена.

| Кто | Работа, которую нужно сделать | Что мешает сегодня |
|---|---|---|

| Кредитный аналитик | «Когда заявка не прошла автоматически, я хочу сразу видеть, почему, и все данные в одном месте, чтобы решить быстро и обоснованно» | Данные разбросаны по системам, непонятно, что сработало в автоматике; решения плохо документированы |

## Ключевые боли и как прототип на них отвечает

| Боль | Решение в прототипе |
|---|---|
| «Не знаю, какой кредит мне нужен» | Подбор по задаче (4 цели), а не по названию продукта; свободный текст → продукт с объяснением, почему он подходит |
| «Опять вводить то, что банк уже знает» | Реквизиты подтягиваются из реестра по ИНН; обороты клиента банка подставляются автоматически; выписка из другого банка распознаётся, а не переписывается вручную |
| «Отправил — и тишина» | Маршрут заявки с живым статусом, понятными «что происходит» и «что от вас нужно», уведомления внутри кабинета |
| «Отказали — и непонятно почему» | Причины простыми словами; вместо бинарного отказа — контрпредложение (меньше сумма, больше срок или другой продукт) |
| «Дозапрос документов по почте» | Дозапрос внутри продукта: список недостающего, загрузка, повторная отправка; сумма и срок при этом защищены от изменений |
| Аналитику не хватает контекста | Карточка: вклад каждого фактора скоринга, лимиты, сработавшие правила, сырые ответы источников, аудит; решение с обоснованием и защитой от параллельных правок |

## Границы MVP (MoSCoW)

**Must — сделано**
- Подбор продукта по цели; 3 продукта с разными правилами.
- Заявка с черновиком, проверкой полноты и дозапросом.
- Обогащение: ЕГРЮЛ/ЕГРИП, ФНС «Прозрачный бизнес», БКИ (симуляторы).
- Прозрачный скоринг и отдельный слой кредитного решения с небинарным исходом.
- Ручное рассмотрение аналитиком.
- Принятие предложения, договор с графиком, подписание и выдача (симуляция).
- Аудит, уведомления в кабинете, RBAC, идемпотентность, ретраи, оптимистическая блокировка.

**Should — сделано частично**
- Распознавание выписки CSV (сделано); распознавание PDF и сканов — нет.
- Метрики конвейера для аналитика (сделано базово).
- ИИ-ассистент на open-weights модели (опционально, с фолбэком на правила).

**Could — не делали сознательно**
- Несколько представителей одной компании с разными правами.
- Поручители, группы компаний, залог недвижимости.
- Персональные предодобренные предложения на главной.

**Won't в рамках хакатона**
- Реальные интеграции, ЭЦП и выдача денег — запрещены условиями кейса, смоделированы.
- Мобильное приложение — запрещено условиями.

### Почему такой MVP

Кейс требует «связанный процесс от обращения до результата» и «согласованность модулей» — поэтому вместо глубины на одном этапе сделан **сквозной путь** через все этапы с минимально достаточной логикой на каждом. Семь персон покрывают все ветки state machine, чтобы жюри могло пройти любой исход за минуту.

## Где ИИ и почему именно там

Кейс просит использовать ИИ «только там, где он создаёт понятную ценность».

| Где | Решение | Почему так |
|---|---|---|
| Подбор продукта по свободному тексту | Опциональная open-weights модель (Qwen2.5 1.5B через Ollama) классифицирует задачу; по умолчанию и при сбое — правила по ключевым словам | Ценность: пользователь описывает ситуацию своими словами. Основной сценарий не зависит от модели — требование кейса. |
| Скоринг и решение | **Без ИИ**, прозрачные правила | Кредитное решение должно быть объяснимым, воспроизводимым и проверяемым. Чёрный ящик здесь — риск, а не ценность. |
| Распознавание выписки | Детерминированный парсер | Для структурированного CSV ML не нужен. Для PDF и сканов — следующий шаг (OCR + open-weights модель). |

## Допущения и упрощения

| Допущение | Почему допустимо | Как будет в продакшене |
|---|---|---|
| Выручка ≈ поступления на счёт | Достаточно для оценки масштаба бизнеса | Классификация операций выписки, данные налоговой отчётности |
| Веса скоринга экспертные | Нет исторических данных о дефолтах | Калибровка на портфеле банка, валидация (Gini, PSI) |
| Внешние источники — симуляторы с упрощёнными контрактами | Условие кейса: автономность и синтетические данные | Реальные интеграции через шину банка, кэширование ответов |
| Подпись — подтверждение в кабинете | Условие кейса | ПЭП/УКЭП, юридически значимый документооборот |
| Выдача — запись о зачислении | Условие кейса | Интеграция с АБС, открытие ссудного счёта |
| Один пользователь — одна компания | Сокращает объём MVP | Доверенности и роли внутри компании |
| Документы хранятся в БД | Простота развёртывания | Объектное хранилище, антивирус, сроки хранения |

## Развитие

1. **CustDev → метрики.** Конверсия «черновик → отправка → выдача», доля автоматических решений, время до решения (уже считается), доля дозапросов.
2. **Предодобренные предложения** для клиентов банка на главной — данные уже есть.
3. **Распознавание PDF-выписок и сканов** через OCR и open-weights модель.
4. **Брокер событий** (Kafka) вместо опроса БД при росте нагрузки; outbox-паттерн для уведомлений.
5. **Калибровка скоринга** на исторических данных, A/B-тест порогов, мониторинг дрейфа.
6. **Роли внутри компании:** собственник подписывает, бухгалтер готовит заявку.
7. **SLA и маршрутизация** очереди аналитиков, назначение по нагрузке.

## Проверка продуктовых гипотез

Фактические интервью и измеренные продуктовые эффекты не представлены. Следующий шаг проверки — дать предпринимателю пройти заявку и сравнить исходные и предложенные условия без подсказок разработчика. До такой проверки потребности и ожидаемые эффекты остаются гипотезами.
